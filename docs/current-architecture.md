# Current architecture

The standalone Bézier learning pilot adds `/bezeg-2.0/learn` and `/bezeg-2.0/learn/bezier-curves`. `learning/content/bezierChapter.ts` holds static bilingual blocks; reading pages use MathJax and sampled SVG previews without mounting a board. `learning/chapter/activities.ts` maps six validated activity IDs to four existing Demonstrations, graph-owned actions, and stable reading sections. No mathematical evaluator is duplicated.

`public/history-entry-bridge.js` transports a small allowlist of chapter navigation IDs and router entry identity through Pages' 404→index redirect. It uses a same-tab, one-use session-storage handoff with a 60-second expiry and exact original URL match, then removes it before restoring sanitized history state. Reading invocation markers carry section/activity IDs for cross-document focus recovery, never pixel offsets. Graph snapshots remain exclusively in app memory; this bridge stores no progress, geometry, scene actions or Presets. If storage or the helper is unavailable, canonical URL restoration still works without inventing predecessor history.

`ChapterActivityVisit` owns the app visit's private activity/ordinary snapshots, reading locations, launch/predecessor identity, ordinary graph return, transition ordering and retry target. Chapter and workspace callers request visit operations rather than coordinating snapshot writes. `useChapterActivity` adapts graph readiness, React notices, router navigation and host cleanup to that owner; language and unrelated query/hash changes do not re-enter a scene. `navigationMemory.ts` is the explicit browser adapter for reading capture, focus/scroll restoration and native-history invocation writes, plus pure history-marker encoding/validation. `ActivitySession` retains graph-owned authored-scene sequencing and rollback; checkpoint data includes view, geometry, graph options and curve selection/editing mode. `GraphHost` calls departure cleanup before disposing its board, closing a Guided lesson before activity capture. Departure releases retry closures even when capture fails, retaining the last valid snapshot. Versioned, validated history markers retain entry/predecessor identity across refresh; geometry and reading pixel offsets stay in memory. Reload reconstructs the authored scene, with a restart notice for a previously active entry. No Preset writes, progress storage, route replacement, or storage migration are introduced. See [visit ownership evidence](reviews/chapter-activity-visit.md) and [pilot evidence](reviews/standalone-learning/implementation.md) for acceptance limits.

Graph appearance is centralized in `src/graphs/styles/GraphPalette.ts` and the existing curve, point, segment, and axis styles. The illustrated C treatment uses moss primary curves, muted comparison curves with line patterns, ochre editable points with cream outlines, dark hover outlines, restrained construction colors, and quiet axes. Scene-order roles are reapplied when curves are added or imported; the single-subdivision lesson keeps its blue left piece and orange right piece. PH auxiliary axes retain their independent visibility behavior. De Casteljau labels use responsive anchors and offsets without changing construction coordinates. The renderer, evaluation, defaults, preset schema, routes, and figure-export lifecycle are unchanged. See [graph visual style](specs/graph-visual-style.md).

The accepted compact tool controls are styled in `WorkspaceControls.css`, loaded after the workspace layout styles. The shared shell uses a localized collapse label with an SVG chevron; native switches and existing control state remain in their original components. On desktop the inspector card takes its height from the graph card (including the navigation footer) and only `#inspector-content` scrolls beneath the fixed heading and tabs; phones let inspector content flow in the page, and no empty scrollbar gutter is reserved ([controls redesign](specs/demonstration-controls-ux.md)). Prototype alternatives are archived at `9886c8d` on `codex/prototype-calm-tools`; production no longer interprets the `variant` query. See [compact controls](specs/calm-tools-prototype.md).

The shared workspace gives the main graph and mounted inspector the available width. Its collection/family/current breadcrumb replaces the permanent family tree; the switcher opens `DemonstrationPicker`, a native modal retaining the active GraphHost, boards, drafts, selection, view, Presentation mode, and lesson session. Graph-owned `pausePlayback` pauses current playback before entry; `pickerUnavailable` covers exports and scene replacement. Cancellation and current-graph selection do not replace the scene. The existing lesson entry path captures the pre-lesson scene when starting the current graph's lesson.

`DemonstrationCollection` supplies the catalogue and picker with one ordered card grid, captured route previews, localized investigation copy, family filtering, and search. Metadata and reviewed lesson availability remain authoritative. `DemonstrationsPage` owns URL filters (`topic`, `q`), history, and validated visit-scoped return state in `demonstrationNavigation.ts`; the picker owns only temporary filters and callbacks. Typing replaces history; topic and clearing actions push. Graph navigation carries the originating catalogue context through later switches. Collection links restore filters, scroll, and card focus; direct graph entry falls back to the unfiltered collection. No Preset or storage migration is required. See [the redesign specification](specs/demonstrations-library-redesign.md).

`LearningPrompt` retains only its prompt index. `WelcomePage` and `HomeDemonstrationsCarousel` retain their homepage composition, metadata choices, and timer/listener ownership. Graph route suffixes, Preset formats and mathematical algorithms remain unchanged.

Collection preview frames reserve their existing aspect ratio with a pale background. Each image reveals after decoding with a 180 ms opacity transition (immediate with reduced motion); failures retain the placeholder. The first three filtered previews load eagerly and the remaining previews use native lazy loading. See [catalog preview loading](specs/catalog-preview-loading.md).

Representative preview recipes run offline against fresh real routes through supported controls, with assertions, fixed framing and provenance. The catalog, picker and selected homepage carousel layer share one graph-free `DemonstrationPreview` component and the same generated poster/media maps. All 45 demonstrations have silent four-second WebM clips that loop while hovered or keyboard-focused, without playback controls. Continuous supported-input sweeps and point drags show changing geometry; degree, continuity and piece counts use exact stepped states. See [continuous motion previews](specs/continuous-motion-previews.md) for the complete capture inventory. The capture script `scripts/demonstration-preview-motion.cjs` records discrete steps, `parameter-sweep` (a range or localized number input driven along a schedule) and `pointer-drag` (an on-board handle dragged along a schedule) modes, with per-frame mathematical assertions declared beside each timeline and in the analysis/curve/concept capture modules. Capture and offline catalog evidence consumers use `scripts/demonstration-preview-capture-api.cjs` for generation, validation and coverage queries; the assembled registry and mathematical helpers stay behind that interface. Tests install fixture specifications through a validator factory rather than mutating the production registry. New stepped captures reuse an exact fixed camera; every new clip checks its first and last source frames against its poster; see [continuous motion previews](specs/continuous-motion-previews.md). Rational weights vary with fixed controls; subdivision captures actual child representations; sampling compares modes at a fixed count. Capture-only observers verify mathematical and presentation evidence, including full-precision board coordinates when a numeric field formats its draft. The player and runtime defaults remain unchanged. See the [per-ID acceptance record](reviews/concept-led-demonstration-previews.md), including the two named runtime presentation dependencies.

The production catalogue displays all entries in metadata order without family disclosures. ## Guided lessons

The repository contains a bounded Guided lesson runtime with explicit explanation, calculation, and observation frames in a graph-cell overlay. Reading temporarily locks graph interaction. Observe on the graph or Hide instructions removes the reading card; a labeled lesson tab in the workspace heading reopens the same frame outside the plotting area, including Presentation mode. Continue lesson advances to the next frame, while explicit Exit lesson restores the entry checkpoint. Visibility is local UI state and never prepares a scene, replaces the board, or changes progress. Hiding pauses active lesson playback; reopening never starts playback. Escape dismisses reading without exiting. Back and Next retain their edge rails; moving backward reapplies the earlier scene. The bounded reading region can scroll at enlarged text or reduced height. MathJax re-typesets changed frames, visibility, and language. Chapter activity entry remains independent. See [the layout decision](specs/lesson-graph-access.md#layout-decision--2026-10-20).

Static content lives in [`src/learning/content/guidedLessons.ts`](../src/learning/content/guidedLessons.ts), separate from route metadata and graph classes. The runtime adapts that content through [`src/learning/runtime/lessonCatalog.ts`](../src/learning/runtime/lessonCatalog.ts) into a narrow typed capability interface. Demonstration-owned adapters retain responsibility for cache invalidation, board updates, auxiliary-object lifecycle, and mathematical meaning. Lesson scenes capture and restore in-memory graph state and do not write Presets. De Casteljau exposes explicit Play/Pause/Replay controls in its observation frame; the graph-owned animation runs one pass from the current parameter to `t = 1`, never autoplays or loops in lesson mode, and is stopped before scene restoration, navigation, exit, route changes, and disposal. The `animation` lesson action has closed id and command unions (`LessonAnimationId`, `LessonAnimationCommand` in `src/learning/model.ts`); a graph registers only the ids and commands it owns and the action registry rejects the rest with `UnsupportedLessonActionError`. [`IterationController`](../src/learning/runtime/iterationController.ts) is the reusable graph-owned driver for iterative playback (fixed step interval, finite iteration limit, completion stops playback, `dispose()`); see [ADR 0012](adr/0012-iterative-playback-controller.md). `IterativeFunctionGraph` (a `BaseFunctionGraph` subclass, Batch C) owns it for `BisectionGraph`, `SequenceGraph` and `FixedPointGraph`: it creates the controller, takes one `transition` callback that advances the model through `commitModel`, resets or pauses it on edits, example changes, scene removal, preset import, lesson animation stop, figure capture and unmount, and builds a fresh controller on a remount after `dispose()`. The iterative lessons reach it only through typed scene actions (`run-bisection-command`, `run-sequence-command`, `run-fixed-point-command`; `next-step` or `reset`, mapped by `lessonCatalog.ts` to the `animation` action for the ids `bisection`, `sequence` and `fixed-point`); Play and Pause remain inspector controls, not scene actions ([ADR 0013](adr/0013-iteration-driven-by-scene-actions.md)). `BaseGraph.beforeFigureCapture()` is a no-op hook called before every single SVG/PNG export and figure batch so a graph with running playback pauses first; `IterativeFunctionGraph` overrides it, and Next step and Play are ignored while a capture is active. The `analysis` family became visible with the three Batch A Demonstrations ([ADR 0011](adr/0011-analysis-family.md)); a family without shipped entries is still omitted from the catalog. The pilot copy and formulas are implementation-ready drafts, but owner/subject-matter review and classroom/device review remain open. See [ADR 0002](adr/0002-guided-lessons-static-content-and-graph-capabilities.md), [ADR 0003](adr/0003-frame-based-graph-anchored-lesson-overlay.md), and the [runtime](tasks/guided-lessons/implement-guided-lesson-runtime.md) and [content](tasks/guided-lessons/study-and-fill-pilot-content.md) tasks.

## Analysis family (Batches A, B and C)

`/bezeg-2.0/analysis/bisection`, `/mean-value` and `/accumulation` (Batch A) and `/extrema`, `/convexity`, `/darboux` and `/taylor` (Batch B) were released on 2026-10-15 and 2026-10-16, and `/sequence`, `/uniform-convergence` and `/fixed-point` (Batch C) on 2026-10-16. The Batch A graphs are `BaseFunctionGraph` subclasses with mathematics in [`src/analysis/`](../src/analysis) (`bisection`, `meanValue`, `accumulation` and their `*Model` parsers) and own the preset collections `bisection`, `mean-value` and `accumulation` (listed in `PresetImport`, whose function-data parsers validate the stored model; mean value rejects `a < c < b` violations and accumulation out-of-range bounds with specific messages). Bisection's history is recomputed from the stored `{example, a, b, step}` and never trusted from a file; playback state is not preset data. `AccumulationGraph` draws the function, the shaded signed region, the accumulation curve and the tangent on a single board: the two curves share the horizontal axis and one y-scale keeps "the slope of A is the height of f" honest, and every graph in the repository owns exactly one session board, so a second board would need new ownership, disposal and capture rules (decision recorded in its class comment). Shared additions: `BaseFunctionGraph.slidingPoint` accepts dynamic bounds and a rejecting `write`, and new lesson parameters, choices and visibility targets extend the closed unions in `src/learning/model.ts`. This batch only adds routes, preset collections and lessons; no existing route, stored preset or lesson identity changed, so there is no breaking change.

The Batch B graphs follow the same pattern with mathematics in `extrema`, `convexity`, `darboux` and `taylor` (and their `*Model` parsers) and own the preset collections of the same names, each with specific import diagnoses. Infima and suprema, candidates, second-derivative signs and Taylor coefficients are computed analytically per named example, never by sampling, and every derived value is recomputed from the stored model. Each board uses a fixed pool of objects whatever the example or parameters. Shared helpers moved into `BaseFunctionGraph`: `escapeHtml`, label and sign text styles, `axisPoint` (a dragged axis point that writes through the rejecting setter and is put back on rejection), `exampleView` (the per-example board view, also applied when a preset of another example is imported) and `memoView` (derived analysis cached on the model's field values, shared by board and inspector). `FunctionLegend` gained the swatch kinds `dashed`, `dashed-line`, `dotted-line` and `ring`, and `NumberInput` an optional `describedBy`. Batch B is additive as well: no breaking change.

Batch C adds `sequence`, `uniformConvergence`, `fixedPoint` and `complex` (with `*Model` parsers and `complexFormat`) and the preset collections `sequence`, `uniform-convergence`, `fixed-point` and `complex-multiplication`. Thresholds, band membership, the reflection two-cycle and grid products are decided in exact integer arithmetic on the documented input grids; suprema are analytic and record whether they are attained. Complex multiplication is a Foundations route (as the [spec](specs/analysis-guided-lessons.md) places it, correcting ADR 0011) whose `ComplexMultiplicationGraph` lives in `src/graphs/complex/` but reuses `BaseFunctionGraph` as a generic flat-model coordinate board. Shared additions: `IterativeFunctionGraph` (above); `BaseGraph.equalAxisUnits` (false for the sequence and uniform-convergence boards, whose axes mean different things, so stored views apply exactly) with a `fitView` hook that restores the example view for such graphs, and `defaultAxesAttributes`; `BaseFunctionGraph` display helpers (`COMPACT_BOARD_WIDTH`, `gridValue`, `stateSnapshot`, stroke and font helpers, a caption `leftEdge`); `FunctionLegend` swatches `dot` and `cross` and the shared `.demo-actions` CSS; and `NumberInput applyOn="confirm"`, which applies typed values on Enter or blur (spinner steps at once) for fields whose value the model snaps. Batch C is additive: no breaking change.

## Geometry and interactive graphs

[`src/bezeg`](../src/bezeg) holds point and curve APIs and mathematical implementations. [`src/graphs/curves/object`](../src/graphs/curves/object) adapts those objects to JSXGraph, including drawing, selection, transforms, controls, and serialization.

Editable polynomial, rational and spline inputs now use numeric `PointImpl` objects. [`ModelPointBinding`](../src/graphs/curves/object/ModelPointBinding.ts) copies drag coordinates into the model and mirrors model changes into the adapter's board point. Replacing or deleting inputs disposes those bindings by identity. Function-backed points remain for dependent spline/PH constructions; this does not change evaluation, sampling or the shared cache revision. PH generating `w` inputs also stay numeric while their auxiliary editor owns bindings.

[`GraphSession`](../src/graphs/base/GraphSession.ts) owns the main board's lifetime, board subscriptions, resize observer, abort signal and coalesced drag-refresh timers. Graph disposal is unconditional; readiness accounts for initialization, deferred refreshes and explicit scene transitions. Graph classes and adapters still own their mathematical constructions and commands. This is the first [ownership foundation](specs/curve-ownership-refactor.md), with wider scene, command and preset-codec migration still outstanding.

[`BaseGraph`](../src/graphs/base/BaseGraph.tsx) is a plain controller class (not a React component) responsible for initializing a JSXGraph board on the container it is mounted on, loading default or saved presets, arranging tools and commands, and exporting images. [`BaseCurveGraph`](../src/graphs/base/BaseCurveGraph.tsx) adds board pointer events, selection, point editing, and curve serialization. Individual demonstrations derive from these bases or related specializations. Graph state lives in a synchronous [`SceneStore`](../src/graphs/base/SceneStore.ts): `setState` applies immediately, so later code in the same tick (for example a later lesson action) reads it, while board side effects run in `onStateChange` once per host commit, preserving React's batching. [`GraphHost`](../src/graphs/base/GraphHost.tsx) creates the controller, mounts it on a container ref in a layout effect, renders the workspace through `useSyncExternalStore`, and unmounts it on route change. Graph behavior is composed rather than overridden where it crosses features: lesson actions are registered per action kind (and target, parameter name or animation) in a [`LessonActionRegistry`](../src/graphs/base/lesson/LessonActionRegistry.ts) through `registerLessonActions`, with shared curve handlers in [`curveLessonActions`](../src/graphs/base/lesson/curveLessonActions.ts); pointer selection and editing modes live in [`CurveEditingFeature`](../src/graphs/base/CurveEditingFeature.ts), which `BaseCurveGraph` composes. JSXGraph curve adapters under `src/graphs/curves/object` contain no React code; their inspector controls are React components in [`src/graphs/base/controls`](../src/graphs/base/controls). Inputs (`OnOffSwitch`, `Slider`, `CountSetter`, the axis selector) are controlled and read live values from the store or adapter; any change made outside React (lesson actions, adapter commands, preset loads) notifies the graph's store so the controls re-render.

All 45 active graph routes use [`DemonstrationWorkspace`](../src/graphs/base/DemonstrationWorkspace.tsx), composed by `GraphHost` from `BaseGraph`/`BaseCurveGraph` panels and Demonstration metadata in `SiteContext`. The shell separates topic navigation, graph, and persistent **Uredi**, **Prikaz**, and **Shrani** inspector sections; the narrow layout places a collapsible inspector after the graph. Presentation and pan/zoom controls are explicit. Route-specific graph and selected-curve command builders remain in **Uredi**; preset and image export controls are in **Shrani**. **Prikaz** renders `BaseGraph.workspaceGraphDisplay()` (graph-specific visibility options, expanded) before the coordinate-system and element-size groups, which are `InspectorDisclosure`s collapsed on each new visit; a display-only switch has one home there, while mathematical parameters stay in **Uredi**. Function graphs order **Uredi** as controls → `renderReveals()` → readout → legend. Shared numeric primitives: `NumberInput` (decimal comma or point, kept drafts), `Slider` (required label with precise entry) and `CountSetter` (− / value / +). The control inventory and accepted exceptions are in [the task record](tasks/demonstration-controls-ux/inventory.md). Structured coordinate editing is used on the general Bézier and PH workflows, with a hodograph editor for PH curves. Other routes retain their existing command builders, including spline-derived point constraints. [`JGBox`](../src/JGBox.tsx) forwards the board container ref; its element ID remains only because JSXGraph derives sub-element IDs from it and CSS/tests select on it. A ResizeObserver adapts all workspace boards to their container, and the workspace routes free their boards on unmount. Legacy presentation CSS remains for non-workspace contexts.

## State and persistence

Graph state lives in each graph's scene store and in mutable curve/board objects owned by that graph. Display settings (element size, coordinate-system mode, point labels) are a per-graph [`DisplaySettings`](../src/graphs/base/DisplaySettings.ts) object reached by style factories through the board's `GraphSession`; they start at defaults on every demonstration. Cached computations are keyed on [version stamps](../src/bezeg/impl/versioning.ts) owned by each point and curve: numeric points stamp every coordinate change, curves stamp structural changes, and a curve's version is the newest stamp among itself and its control points. Values whose inputs cannot be tracked (closures without declared dependencies, Farin slider weights) are volatile and never cached. Cosmetic size changes redraw the board without invalidating mathematical values, and geometry implementations no longer depend on graph infrastructure.

Transient state is graph state outside Preset data and the scene store that changes what is drawn or what controls show: curve selection, a rational curve's standard form and effective weights (Preset DTOs store display-normalized weights in standard form), the elevation overlay, the PH hodograph view and De Casteljau playback. The repeated-subdivision step count is derived from the number of pieces, not kept. Each graph declares it once through `captureTransientState`/`restoreTransientState` (an undefined value means the fresh-scene default), and declares the drawing that a Preset import does not rebuild through the idempotent `syncReplacedScene`. `BaseGraph` owns every scene replacement path and applies both in a fixed order (Preset data, scene state, transient state, scene sync): mount, Preset load, reset and import, figure batch scenes and entry restore, lesson checkpoints and the lesson default scene. Lesson checkpoints and the lesson default scene replace the scene state rather than merging it, restore synchronously so a rollback within one tick is drawn before the host commits, and advance the workspace revision so scene-backed controls and the PH hodograph board are rebuilt. Each Preset in a figure batch is captured with fresh transient state, as loading it would show; the entry scene's transient state is restored afterwards. The De Casteljau graphs keep their drawn parameter as a documented drawing cache of the scene-store `t` (playback publishes `t` at a display cadence); saved scenes use the drawn value through `sceneGraphState`, and every replacement resets the cache from the restored `t`. Transient state lives only in in-memory checkpoints and batch entry scenes: it is never written to Presets, URLs or progress, and the Preset format and routes are unchanged. The parametrized real-graph test [`GraphTransientState.test.tsx`](../src/graphs/base/GraphTransientState.test.tsx) covers every Demonstration in `graphFactories`; see [task 01](tasks/graph-contract-deepening/01-graph-transient-state.md) for the inventory and [ADR 0015](adr/0015-graph-transient-state-declaration.md) for the decision.

[`PresetService`](../src/graphs/base/presets/Presets.ts) saves named presets under a `bezeg-2.0:` browser-storage namespace while retaining the established `preset-` keys inside the values and exported files. [`src/storage/appStorage.ts`](../src/storage/appStorage.ts) isolates these keys and the language preference from the original app sharing the `efodx.github.io` origin. Existing exported preset files remain explicitly importable through the validated file-import flow, and exports keep the same interchange keys. Presets can contain curve data, board bounds, and graph state. [`PresetSelector`](../src/graphs/base/PresetSelector.tsx) supplies saving, selection, deletion, text-file import/export, and batch image generation. The graph controller owns the selected preset; select, save, delete, reset and import replace the scene in place through the same scene-replacement path as figure batches, without remounting the workspace.

This release uses a new public route base, `/bezeg-2.0/`. Browser-local presets from the original site remain under its original keys, so users who want them in this release must export a preset file from the original site and import it explicitly.

[`ClassMapper`](../src/graphs/curves/object/ClassMapper.ts) serializes curve types using string identifiers. Some identifiers retain the older `JSX` prefix even when the class is named `JXG`. Renaming them could affect saved files and browser presets.

There is no server or database implementation identified in the inspected application source. The owner confirmed that stateless means no backend, accounts, or server database, while browser-local presets and file exchange remain allowed. See [ADR 0001](adr/0001-static-client-only-app.md).

| Demonstrations | Defaults, parameter state, specialized constructions, and graph-level controls in [graph classes](../src/graphs/curves). |
| React controls | Sliders, counts, switches, modal dialogs, and command builders call mutable graph/curve methods. |

Polynomial evaluation uses recursive linear interpolation (De Casteljau). The same triangular scheme supplies displayed constructions, subdivision control points, and extrapolation. Degree elevation constructs a new polynomial representation. Rational evaluation uses weighted interpolation; subdivision/extrapolation operate on homogeneous coordinates and project back, while elevation blends weighted coordinates and weights. Geometry methods return new curves; adapters replace points or register resulting board curves.

Spline objects assemble polynomial pieces and derived control points for the specified continuity construction. Global evaluation selects a piece using normalized parameter spans and converts to that piece's local parameter. Spans are proportional to endpoint chord length raised to α. This differs from the fractional parameter transformation in the weighted polynomial/PH demonstrations.

PH geometry uses a start point and generating `w` points to derive a polynomial curve and rational offsets. Evaluation delegates to the underlying polynomial. PH speed/arc-length routines support uniform sampling; parameter inversion uses a predictor and four Newton corrections. Degenerate speed or rational denominators are not comprehensively guarded by this implementation. This inventory describes algorithms without certifying their numerical correctness over all inputs.

## Interaction and update flow

Point dragging stamps the dragged model point's version; callback-based JSXGraph curves also receive a coalesced full-board refresh so their separate X/Y callbacks observe the new geometry even when the board is already processing an update. Curve-wide gestures pass through board down/move/up handlers in `BaseCurveGraph` and adapter transform methods. Geometry setters stamp versions on the mathematical objects; the graph layer no longer notifies any cache. Sliders and switches update React state, mutable geometry, board attributes, or combinations of these. Construction caches use both the curve version and the construction parameter where applicable. Separate X/Y callbacks can ask for the same curve evaluation twice; cached evaluations reduce repeated work while the curve version is unchanged.

Before replacing a curve scene, `BaseCurveGraph.importPresetData` disposes each curve's base JSXGraph objects, including control-polygon, convex-hull, and bounding-box auxiliaries, before removing shared graph points. This keeps stale auxiliary objects from corrupting JSXGraph's update state during guided-lesson transitions. Specialized curve constructions may still own additional objects and remain responsible for their own cleanup.

Graph-level and selected-curve commands remain distinct paths: `getGraphCommandsArea()` swaps to the selected-curve area. The shared workspace keeps editing, display, and save sections mounted when switched or hidden. Polynomial operation preview objects are initialized in an effect, with explicit preview buttons, rather than created while rendering command arrays. Numeric point forms resolve current points when applying coordinates, including PH points replaced by the hodograph editor. The uniform PH parameterization route adds its comparison controls to the workspace editor so they remain available alongside the PH tools.

Guided lesson scenes use the graph capability seam for renderer-owned visuals. The Bézier evaluation scene renders its reviewed worked example in the lesson panel and asks the curve adapter to mark the evaluated point at `t=1/2`; the marker is included in curve state so scene restoration removes it when the lesson advances or closes.

The PH editor initializes once per mount and adds a child board whose draggable `w` points are wrapped as geometry points. Disposal snapshots the current generating points, removes the parent-child relationship, disconnects its resize observer, and frees the auxiliary board. Workspace routes disconnect their main observer and free their main board on unmount. Legacy main-board disposal remains a separate engineering gap. Child cleanup uses the captured parent board rather than a parent component field that may already have been cleared.

## Preset contract and current failure modes

`PresetService` stores each demonstration's collection at `preset-<demonstration-id>` as `{ data: Preset[] }`. Each preset has `id` and optional `data`, `boardState`, and `graphState`. Board state stores the bounding box; curve graph data is an array of `[typeIdentifier, curveDto]` entries. DTO content is type-specific: polynomial points/state, rational weights, PH generating points, or spline construction settings. `ClassMapper` dispatches to static `fromDto` / `toDto` methods.

The selected name is route-local and owned by the graph controller; changing it replaces the scene in place and resets the view before the preset's own bounds apply. Loading restores bounds/state/data when present, otherwise the graph uses its default geometry and then calls `initialize()`. Some initializers regenerate objects or reset bounds, so restoration behavior must be checked per graph. Curve import explicitly clears selection.

Export scans the release's namespaced storage for keys beginning `preset-` and writes a single JSON object to `presets.txt`. [`PresetImport`](../src/graphs/base/presets/PresetImport.ts) validates recognized collections, DTO types, finite numeric data, graph bounds, required curve state, spline parameters, and PH degree before writes. The import dialog lists matching collections for replacement consent and keeps errors visible. Commit revalidates and attempts rollback on storage failure. Saving an existing name replaces geometry, board state, and graph state together. Preset interchange keys, DTO identifiers, and file shape remain unchanged; browser storage uses a release prefix, and arbitrary storage entries and malformed data formerly accepted by the unsafe importer are rejected. Per-graph display settings are not serialized in presets. PH offset visibility lives only in the curve adapter state (its DTO); the graph scene state no longer carries `showOffsetCurve` or `showOffsetCurveControlPoints`, and stored presets or checkpoints that still hold those graph-state keys load unchanged because the extra keys are ignored. The selected-curve operation controls and the editing-mode dropdown read adapter and scene state on each render rather than keeping local copies.

## Export pipeline

[`FigureCapture`](../src/graphs/base/export/FigureCapture.ts) receives an explicit current container, SVG root and graph-session lifecycle. SVG serializes a clone of the renderer tree with the visible HTML labels added; PNG still uses `html2canvas` on the board DOM. Both wait for graph work, fonts, current-container MathJax typesetting and images. Each wait is bounded, graph disposal cancels the operation, and late work cannot trigger a download. PNG hides only target-container assistive MathJax nodes and restores their exact display styles. Blob downloads revoke owned object URLs. [`SvgMathLabels`](../src/graphs/base/export/SvgMathLabels.ts) adds each visible `div.JXGtext` label to that clone: formulas are re-typeset from their MathJax source by a lazily imported `mathjax-full` SVG output (glyph paths, no fonts, own lite adaptor, loaded only on the first SVG export) and placed as nested `<svg>` elements at their on-screen boxes; plain labels become `<text>`. The live DOM is not modified and a typesetting failure fails the export ([spec](specs/svg-export-math-labels.md), [ADR 0008](adr/0008-export-time-mathjax-svg-typesetting.md)).

[`PresetFigureBatch`](../src/graphs/base/export/PresetFigureBatch.ts) captures selected presets through a live graph owner and keeps PNG blobs local to one job before creating `slike.zip`. It awaits scene readiness instead of a fixed remount delay and restores the entry scene on success or failure while its session is alive. BaseGraph integrates scene disposal, reconstruction and each graph's declared transient state and scene sync (see State and persistence); graph subclasses declare extra constructions and PH child-editor state there, and `BaseCurveGraph` declares selection. Overlapping batches on one owner are rejected; cancellable scene operations receive a signal to suppress stale callbacks. Capture does not change browser presets or the selected preset. Graph controls are temporarily unavailable during a batch. Running De Casteljau animation is restored paused at its entry parameter.

## Rendering investigation candidates

- [`AbstractJXGPointControlledCurve`](../src/graphs/curves/object/AbstractJXGPointControlledCurve.ts) gives JSXGraph separate X and Y callbacks, each calling `eval(t)`.
- [`PolynomialBezierCurve.eval`](../src/bezeg/impl/curve/polynomial-bezier-curve.ts) caches evaluated points by parameter while the curve's version is unchanged. The first performance experiment adds point-only polynomial and rational interpolation on cache misses, avoiding copied intermediate rows and a duplicate result allocation. Full De Casteljau tables remain available for displayed constructions and other curve operations; sampling is unchanged. See the [performance spec](specs/bezier-drawing-performance.md) for scope and verification.
- Point dragging and several graph operations advance the shared cache revision. Broad invalidation may cause unrelated geometry to be recomputed.
- Board updates, mathematical evaluation, auxiliary constructions, and React remounting are separate potential costs. Measure them separately before choosing an optimization or replacing JSXGraph.

These are source-based hypotheses. No benchmark, browser profile, mathematical regression check, or runtime UX assessment has been performed during this discovery pass.
