# 02 Declaration contract and conversion tooling

Source: [board workspace spec](../../specs/ux-picks-app-wide.md) requirements A1, A8 and "Converting all graphs"; [ADR 0065](../../adr/0065-graphs-declare-presenters-render.md).

## Goal

The first complete version of what a graph and a lesson frame declare, with the tests and scripts that make converting a demonstration mechanical and machine-checked. Tasks 04 to 07 may add fields while they are proven on the pilots; the contract is frozen at the gate before task 08, not here. Reference: `src/uxPicks/declare/graphUx.ts`, `night/GUIDE.md`, and the contract gaps in `docs/reviews/ux-picks/trial-report.md` and the state note ("Contract gaps reported by converters").

## Slices

1. **Contract types** (handler-owned design): parameters with key, kind (`range`, `count`, `choice`, `toggle`), range, step, format, label, help, and placement (board or Orodja); formula with label; readout groups, rows (`valueTex`, legend link), notes; legend entries bound to drawn objects, including the kinds the prototype lacked (`ring`, `cross`); section cards; actions (a button the graph offers, such as "Pokaži oceno napake" or "Naslednji korak"); view marks; status lines. A lesson frame declares the controls and actions its text asks the learner to use (spec A9), next to its opened cards and highlighted rows. Each parameter is the binding of task 01 (reader and the graph's existing setter) plus its presentation; keys reuse `FUNCTION_PARAMETER_NAMES` (`src/learning/model.ts`) where a name exists. Per-graph id unions; a typed frame builder per lesson content file checks a frame's ids against its graph's union (`LessonFrame` and `LessonDefinition` stay non-generic, and there is no central id map). Located with the graph base code, independent of React and JSXGraph.
2. **Shared gaps closed once:** every shared range or count input takes a declared parameter; one shared lesson step builder carries frame declarations for all lesson files (the prototype copied ten lines per file); frames can highlight notes.
3. **Contract test** (built on `src/learning/content/sceneContentAgainstGraphs.test.tsx`, which already runs lesson scenes against graphs; that suite is sampled in local runs, so this one must cover every frame in CI): for every declaring graph and each of its lesson frames, run the scene's actions synchronously, evaluate the declaration, and fail on unknown ids, a highlighted row or opened card absent in that scene's state, more than three highlighted rows, a legend entry whose object is not drawn, a used control that does not exist or is locked in that frame, or text not from the catalog. Whether a frame's text asks for a control cannot be machine-checked (nothing is inferred from prose): the conversion guide makes it a converter's step per frame, and the inventory script lists frames whose text contains a control's label as candidates. Taylor step 1, part 3 of 5 ("Pokaži oceno napake") is the worked example.
4. **Parity by golden values:** a tool records what a demonstration's present panel shows over sampled states, before the panel is removed; the declaration must reproduce the recording. Recordings are deleted in task 10.
5. **Inventory script:** per registered demonstration (`src/graphs/**/runtime.ts`), its graph class and base classes, shared panels, controls and ranges, readout rows and catalog keys, new strings that need keys, legend entries, board captions, lesson files, frames naming values or controls, its own test files, and its blocker class. It also reports surface demonstrations, point-set graphs, graphs with playback, and controls living outside `BaseGraph` (the Playground's sliders). Output is the authoritative count, the work list and the connected components for task 08, and it names the legacy-`step()`, surface and point-set pilots.
5a. **Preview mechanism, decided here** ([parameter writes](../../specs/parameter-writes.md) "Previews"): build a shadow board (option B) and geometry from state (option A) for Taylor, De Casteljau and phase portrait; measure capture cost and frame gaps at 1× and 4× CPU throttle under [the performance plan](../../performance-plan.md); record the choice in a new ADR. It is decided before the contract freezes because option A adds a pure geometry function to every conversion, and because part of a curve graph's scene (board points) is not in its state, which a shadow board built from copied state must account for.
5b. **Catalog cost and ownership:** the prototype used inline Slovenian, so the number of new `sl`/`en` keys is unknown; the inventory counts them. Keys are type checked, so the handler adds each round's keys before its lanes start. Evaluate per-family catalog fragments as the alternative and decide; this is not left open.
6. **Per-graph check recipe:** contract test, parity test and browser probe for one graph, with a short summary a worker can paste.
7. **Conversion guide** in the repository, replacing `night/GUIDE.md`, including the highlight rules, the catalog rule, and the placement rule for controls with worked examples from the pilots: which choices and toggles go on the board, which controls stay in Orodja, and why.
8. **Pilots declared:** the eight pilot graphs declare themselves and pass the recipe. Nothing renders the declarations yet.

## Acceptance

- The eight pilots pass the per-graph recipe; the contract test fails on a seeded wrong id, a hidden highlighted row and an undrawn legend entry (observed failures recorded).
- Converting a plain pilot touches its graph file, its lesson files and its own tests only; the files touched per pilot are recorded as the sizing input for task 08.
- The preview ADR exists with its measurements; the catalog decision is recorded.
- `npx tsc --noEmit --pretty false` and the production build pass; `sl.ts` and `en.ts` are in lockstep.
