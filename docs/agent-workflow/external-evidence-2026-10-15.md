# External evidence on coding-agent delegation and model effort

Sources checked 2026-10-15. This note covers what primary sources establish about task handoffs, context isolation, token cost, coding-agent coordination, and the proposed Claude model/effort choices. None measures performance in Bezeg.

The owner subsequently authorized adopting and simplifying these proposals on 2026-10-15. The assessment below records the review before that implementation; use [the maintained workflow](../agent-workflow.md) and [evaluation spec](../specs/agent-workflow-evaluation.md) for current policy.

## What delegation evidence supports

Anthropic’s [multi-agent research system report](https://www.anthropic.com/engineering/multi-agent-research-system) reports a 90.2% improvement for an Opus 4 lead with Sonnet 4 workers over a single Opus 4 on an internal research evaluation. The work was breadth-first research: independent agents followed separate leads and returned compressed findings. The same report says multi-agent research used about 15 times the tokens of ordinary chats, and explicitly cautions that coding usually has fewer truly parallelizable tasks, more shared context, and coordination problems. Its 3–5-worker configuration reduced time by up to 90% on complex research queries; that result does not justify a general 3–5-worker coding rule.

The [Science of Scaling Agent Systems paper](https://arxiv.org/abs/2512.08296) provides a more direct coding comparison. It tested 260 configurations across six agentic benchmarks, five architectures, and three model families while matching total compute. On SWE-bench Verified, the single-agent mean was 52.2%; all four multi-agent architectures scored lower: hybrid 51.1% (−2.1% relative), centralized 50.6% (−3.1%), decentralized 49.4% (−5.4%), and independent 44.4% (−14.9%). The authors used only 20 SWE-bench instances per configuration because of evaluation cost. This is evidence against assuming multi-agent coding always helps, but it does not test a human-directed handler assigning one independent implementation slice and reviewing the patch. The study’s “87%” figure is accuracy at selecting a best architecture on held-out configurations, not an 87% coding-success gain.

[CooperBench](https://arxiv.org/abs/2601.13295) tests a different, riskier form of collaboration: two agents implement separate features that may conflict, using an agent-to-agent message tool; the merged implementation is checked against both features’ tests. The solo baseline assigns both features to one agent. Across 652 tasks in 12 repositories and four languages, authors report collaboration averaging 30% lower success than one agent doing both tasks. For GPT-5 and Claude Sonnet 4.5, the plotted rates are about 47–48% solo versus 26–28% cooperative. Giving agents a communication tool did not significantly improve cooperative success, although it reduced merge conflicts. A small 46-task experiment fell from 68.6% success with two agents to 30.0% with four. These results warn about peer coordination; they do not evaluate the handler-led, bounded-slice workflow proposed for Bezeg.

The [Claude Code subagent documentation](https://code.claude.com/docs/en/sub-agents) describes the relevant handoff mechanics: a subagent gets a fresh, isolated context, does not inherit the main conversation, and returns a summary. The docs recommend subagents for self-contained work that can return a summary; they also note that each agent spends its own tokens and that many detailed returns consume significant main-context space. Anthropic’s research report similarly recommends giving each assignment an objective, output format, tool/source guidance, and clear boundaries, because vague assignments led to duplicated work and gaps. A minimal implementation handoff should therefore contain the goal and acceptance criteria, owned files or module, necessary spec/context and dependencies, required checks, and a short result format covering changes, checks, and unresolved risks. This is a synthesis of the docs, not a tested optimal prompt.

## Model and effort fit

Anthropic describes [Haiku 5.5](https://www.anthropic.com/claude-haiku-5-5) as a fast, cost-sensitive model for high-volume and narrow work, including summaries and subagent tasks; it says Haiku pairs with Sonnet or Opus on coding work. Its published coding results are 39.2% on Terminal-Bench 4.0, compared with Sonnet 5.5 at 70.6%, and 46.4% on FrontierCode 1.1 compared with Sonnet’s 52.1% at xhigh. The FrontierCode table does not specify Haiku’s effort setting, so that score is not a matched-effort comparison. The launch page calls Sonnet and Opus the better choices for complex agentic coding. Haiku 5.5 supports xhigh and max effort, but I found no public Haiku effort sweep on coding tasks. Thus Haiku xhigh is technically supported, but evidence does not establish it as a good default for routine exploration; the model is positioned for narrow, cost-sensitive subagent work.

For [Sonnet 5.5](https://claude.dev/blog/building-with-claude-sonnet-5-5/), Anthropic recommends medium for well-specified agentic coding and day-to-day engineering, with high for harder or longer tasks; it advises using xhigh or max only if evaluations show a quality gain. Medium is also Claude Code’s default for Sonnet 5.5. This makes Sonnet medium a defensible starting point for bounded implementation, not a Bezeg-specific winning setting. Anthropic’s public effort-level coding examples in [“Spending your effort”](https://claude.dev/blog/spending-your-effort/) compare Opus 5.5 and Fable 5.1, not Haiku or Sonnet, so do not transfer those gains directly to either proposed worker setting.

One handler with a bounded worker, clear ownership, and independent acceptance is a reasonable design inference from these sources, not a directly validated winning architecture. Add parallel workers only for independently owned slices. The model and effort choices remain hypotheses to record and compare locally; current sources do not establish local performance.

## Codex guidance and context cost

OpenAI's [subagent guidance](https://learn.chatgpt.com/docs/agent-configuration/subagents) recommends Luna for narrow tasks, High as its explicit starting effort, and Max/XHigh for demanding reasoning. It recommends GPT-6.1 Sol for demanding agents. These are vendor recommendations, not a matched Luna High versus Max coding experiment. The [Luna model page](https://developers.openai.com/api/docs/models/gpt-6-luna) confirms support for both efforts. No matched Bezeg-like comparison was established by this research.

Files on disk do not consume model context until their content is included. [AGENTS.md discovery](https://learn.chatgpt.com/docs/agent-configuration/agents-md) automatically loads applicable instructions; ordinary linked documents need a read. [OpenAI's skills guidance](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra) recommends loading conditional details only when needed. Fresh worker briefs can exclude the parent's exploratory conversation where the tool supports it; they still need applicable project constraints, acceptance criteria, and decisions. In this session, selecting a worker model/effort requires `fork_turns="none"`, which makes the self-contained brief necessary.

[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) can reduce repeated-prefix processing costs, but does not remove those instructions from the model's context. [Subscription usage](https://learn.chatgpt.com/docs/pricing) depends on model, context, reasoning, tools, and caching; API dollar rates do not estimate included Codex tasks. Optimize accepted-work cost and time, including review and repairs, rather than file length alone.

Empirical findings on context files are mixed. [Evaluating AGENTS.md](https://arxiv.org/html/2602.11988v1) found generated files increased average inference costs by 20% and 23% on two benchmarks, with small average success reductions; developer-written files generally helped modestly. [A different study](https://arxiv.org/html/2601.20404v2), using GPT-5.2-Codex on 124 small PRs in ten repositories, found median runtime 28.64% lower and median output tokens 16.58% lower with instructions. The second study only sanity-checked outputs rather than comprehensively testing correctness. Neither estimates this repository's savings from shortening a file. Useful, task-relevant instructions can save exploration and rework; redundant requirements can add both.

## Assessment of e007f6c and proposed starting flow

This is a recommendation for discussion; active workflow instructions and model defaults are unchanged.

The commit improves assignment boundaries, verification evidence, honest unknowns, and comparisons between similar tasks. It does not change model defaults. A later commit, `729b508`, changes Sonnet from High to informal "normal"; use the actual supported effort name when configuring or logging it.

Simplify these parts before treating the workflow as settled:

- Consolidate repeated model, dispatch, return, and no-substitution rules. At review time the workflow is 1,423 whitespace-separated words; the evaluation skill is another 740. These are word counts, not measured tokens. Keep runtime guidance separate from research and evaluation history.
- A six-field handoff is useful. Keep the existing preference for separate research and implementation conditional: direct implementation is reasonable when the worker can cheaply locate the change. Use exploration when it resolves a real uncertainty or isolates substantial noisy work.
- Three or five tasks per setting is a pilot budget, not statistical assurance. Small samples can reveal failures or suggest another test; they cannot validate a universal default.
- The proposed research-effort pilot needs role-specific records: the current logger covers implementation tasks. Research quality does not establish implementation quality.
- Preserve defaults during a task, but permit an explicitly chosen provisional default based on external guidance. Requiring local comparative evidence before reconsidering any untested starting preference gives that preference undeserved authority.

A reasonable balanced starting policy is Luna High for bounded Codex exploration and implementation, Haiku medium for narrow Claude exploration, and Sonnet medium for bounded Claude implementation. Reserve harder reasoning or a stronger model for tasks with substantial ambiguity, mathematical constraints, or demonstrated reasoning failures. Assess foreseeable difficulty before dispatch; first distinguish missing context or a bad task boundary from insufficient reasoning. These are provisional recommendations, not measured winners, and do not authorize silently changing the current policy.

Keep the handoff to: role/edit permission; goal and checkable acceptance; owned scope; relevant source/decisions/dependencies; required checks; concise return evidence and gaps. Start with one worker and add independent slices as useful. The handler reviews the actual diff and integrated behavior. Workers need their assignment and relevant project rules; model-routing rationale, accumulated logs, and external research belong with the handler when evaluating the workflow.

For ordinary tasks, record task/role/size, selected and observable resolved settings, acceptance and coverage gaps, repair rounds, and failure cause. Capture dispatch and acceptance timestamps prospectively. Record total handler-plus-worker usage only when exposed, with its scope; otherwise mark it unknown. Add detailed handoff/concurrency fields when investigating those factors. Compare one factor at a time on similar work with stable checks; read-only repeats or isolated checkouts can give cleaner comparisons without competing writers. A research pilot only informs research routing.
