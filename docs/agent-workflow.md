# Agent workflow

The handler owns scope, integration, acceptance, and Git operations under [AGENTS.md](../AGENTS.md). Delegate substantial, separable work; keep small or tightly coupled changes with the handler. Workers own their assigned slice and evidence, without further delegation, commits, or pushes.

GitHub's [master ruleset](https://github.com/efodx/bezeg-2.0/rules/25172820) blocks non-fast-forward updates to `master`. Worker Git ownership remains an instruction in the shared environment, with the [enforcement limits](specs/agent-workflow-evaluation.md#git-controls) documented separately.

## Model routing

These are provisional starting choices based on [external guidance](agent-workflow/external-evidence-2026-10-15.md), not measured Bezeg winners. Select the active orchestrator's column and check the tool's supported model and exact effort names before dispatch.

| Assignment | Claude orchestrator | Codex orchestrator |
| --- | --- | --- |
| Narrow research and code exploration | Haiku 5.5 `medium` | GPT-6 Luna `high` |
| Bounded implementation, fixes, and tests | Sonnet 5.5 `medium` | GPT-6 Luna `high` |
| Independent review | Sonnet 5.5 `medium` | GPT-6 Luna `high` |
| Narrow browser smoke ([smoke-tester](../.agents/skills/smoke-tester/SKILL.md)): named routes, repair rechecks, catalog/asset checks | Haiku 5.5 `medium` | GPT-6 Luna `max` |
| Broad or first-pass browser smoke of new UI | Sonnet 5.5 `medium` | GPT-6 Luna `max` |
| Integration and final acceptance | Handler | Handler |

Choose supported higher effort or a stronger model within the active family for substantial ambiguity, difficult mathematics, or complex interactions; record the reason and selected setting. Assess foreseeable difficulty before dispatch. After a failure, distinguish missing context, unclear acceptance, ownership conflicts, environment problems, and reasoning errors before escalating. Reserve XHigh/Max for demanding reasoning or a labeled comparison. If the intended setting is unavailable, report it and continue independent work; do not silently substitute across families. Requested settings are not proof of resolved settings.

Codex child defaults are in [`.codex/config.toml`](../.codex/config.toml); the handler retains its selected model. Claude applies this table through its available dispatch tool. Explicit task settings override defaults.

Under Claude, dispatch implementation, fix, and review workers as `bezeg-worker` and browser smoke as `bezeg-smoke` ([`.claude/agents/`](../.claude/agents/)), passing the table's model. They carry only shell and file tools and no skill listing, so a worker starts near 9k input instead of 37k under `general-purpose` ([evidence](agent-workflow/haiku-context-2026-10-25.md)). They cannot invoke skills: name skill and checklist paths in the brief. Use `Explore` for read-only research, and `general-purpose` only when a role needs another tool; record why.

## Dispatch

1. Read the relevant spec and acceptance criteria, inspect existing changes, and estimate task size before dispatch. Start with one worker; parallelize substantial slices only when their behavior and write ownership are independent, and run at most three workers at once: more concurrency spends the five-hour session limit in minutes without lowering total usage ([evidence](agent-workflow/lesson-run-usage-2026-10-25.md)). Give shared interfaces and integration files one owner; serialize dependencies. Identify shared verification resources even for file-disjoint slices, and coordinate changes to shared dependencies such as linked `node_modules`. Concurrent Playwright runs use distinct `SMOKE_PORT`s, which also separate their output folders, or run serially.
2. Use exploration separately when it resolves substantial uncertainty or isolates noisy work. Otherwise let the implementing worker investigate its bounded slice. Pass useful findings forward rather than repeating the same exploration.
3. Prefer a fresh context when supported. Supply a self-contained brief using the fields below, relevant project constraints, and settled decisions. Name useful entry files or spec sections; workers start there and expand investigation as needed for acceptance, returning focused excerpts and check results. Research history, workflow evaluation, and model-routing rationale stay with the handler. A fresh conversation still needs applicable repository rules. Size each slice to finish in about 20 worker turns, since workers reached their budget at a median of 26 turns ([evidence](agent-workflow/lesson-run-usage-2026-10-25.md)); split larger specs into sequential workers linked by handoff notes. Input budgets are 100k for Haiku workers and 150k for others. When a returned worker is past its budget and the next step does not need its history, start a fresh worker from its handoff note instead of continuing it. Workers account for most usage because every turn re-reads their accumulated history ([evidence](agent-workflow/claude-turn-usage-2026-10-24.md)).
4. Before delegated browser verification, establish a stable checkout/build and confirm the preview is reachable from the worker's verification environment. Supply preview ownership, revision/dirty state, and setup status. If access cannot be confirmed until the worker connects, make that its first bounded check; return access failures to the handler and mark dependent coverage blocked before repeated setup attempts. Under Codex, run loopback previews and Playwright outside the sandbox from the first attempt; sandboxed loopback failed in every recorded browser task. Subagents have no in-app browser: assign Playwright-based checks, or decide a handler-operated relay at dispatch.
5. Capture the task start/dispatch timestamp from a clock command at dispatch, requested worker settings, and brief revision (`handoff-v12` below). Retain resolved settings or scoped usage if tool results expose them; configured defaults describe intent, not runtime resolution. Keep a source reference or short excerpt of the task-specific acceptance, context, and checks for later feedback; whole conversations are unnecessary.
6. Watch worker budgets from the handler, since workers usually cannot see their input. Under Claude, start the watcher for every background worker, research and smoke included: after each launch, a project hook (`tools/agent-usage/claude_watch_reminder.py`) prints the exact `python tools/agent-usage/claude_worker_watch.py <agentId> --until <threshold>` command for the worker's resolved model. Run it as a background command; when it exits at the threshold, send the worker `HANDOFF` with `SendMessage`. Messages arrive at the worker's next tool round, and a probe stopped about 12k past the signal. Thresholds are 78k for Haiku, so the stop and handoff note stay under its 100k budget, and 135k for other models. Under Codex, start `node tools/agent-usage/codex_worker_watch.cjs --agent-path <canonical-worker-path>` after each dispatch and follow the [monitor and relay procedure](../tools/agent-usage/README.md#codex-monitor-then-relay). Consume its terminal event while the worker runs: on `handoff_required`, send `HANDOFF` with `send_message`; on `completed`, inspect the result; on telemetry failure, report the gap and retain the turn fallback. The [control probe](agent-workflow/codex-handoff-probe-2026-10-24.md) confirmed messaging and interrupt/follow-up. Automatic detection requires the handler relay; the 15k margin is not a proven Codex ceiling.

### Handler context budget (Claude)

Under Claude, the handler also hands off its own context, since every handler turn re-reads it and a handler that kept everything cost as much as all its workers ([evidence](agent-workflow/lesson-run-usage-2026-10-25.md)). Codex handlers have no self-watch yet; this section does not apply to them.

1. When delegated work starts, run `python tools/agent-usage/claude_worker_watch.py --self --until 150000` as a background command.
2. At that soft threshold, dispatch no new workers and start no new step. Finish the current step, let running workers return, integrate and verify what they delivered, then start the same watcher with `--until 190000`.
3. If the 190k watcher exits first, send `HANDOFF` to every running worker and collect their notes instead of waiting for completion.
4. Commit verified work under the Git rules. Push accepted work to `master`; push other progress to the working branch on `origin` so it survives.
5. Write a handler handoff note to `docs/reviews/<feature>/handler-handoff-<n>.md`: branch and commit, source spec and tasks, accepted work, remaining steps in order, worker handoff notes, checks run with their revision, open decisions and risks, and the settings to keep (model, permission mode, worker routing).
6. From the current working directory, launch the successor with `claude --bg -n "<feature> handler <n+1>" --agent claude --model <own model> --permission-mode <own mode> "<prompt>"`, where the prompt names the note and asks the successor to continue under `AGENTS.md`. It runs in the same worktree and branch. End the turn with the printed session id, note path, and commit.
7. Do not launch when the remaining work needs an owner decision or would repeat a failed step, or when the launch fails; end with the note path and a paste-ready prompt instead.

### Assignment brief: handoff-v12

- **Role:** research, implementation, review, or smoke; edit permission.
- **Goal:** outcome, source spec, and checkable acceptance.
- **Scope:** owned paths/modules, shared owners, existing changes to preserve.
- **Context:** relevant entry files/spec sections, settled decisions, dependencies, shared verification resources and their owners; for browser checks, preview ownership, revision/dirty state, and reachability/setup status. When the slice touches stored Presets, imported files, or routes, state that data and links valid at HEAD must keep working, or name the accepted break and its recorded impact.
- **Checks:** map each acceptance criterion to worker checks, handler checks, or sufficient existing evidence. For each new regression assertion, report an observed failure against the pre-change code or a deliberate mutation. For controls or graph state, check control values and the graph/board after applicable indirect changes: Reset, lesson actions, preset restore, and language switch. For UI work, name applicable routes, viewports, text enlargement, and interactions where required by the spec. Describe presentation goals as visible results, such as a rail visible over child backgrounds or intended headline wrapping at a named viewport.
- **Return:** changes or findings, observed check results, decisions/risks, and unverified cases, within a stated cap (≤N words or lines, flags with `file:line`). Write bulky evidence (inventories, full logs, raw reports) to a named file path and summarize it in the reply. Flag missing or conflicting instructions and mathematical contradictions encountered in the slice; the handler settles contradictions before dependent work proceeds. Ordinary implementation details need no narration.
- **Budget:** every turn re-reads the worker's history, and code output costs about 2 characters per token. Locate with `grep -l`/`-c` before `grep -n`, batch searches into one command, read at most about 150 lines per call and never a whole file over about 300 lines, quote `file:line` instead of pasting code, and send full test, build, and diff output to log files. On a `HANDOFF` message from the handler, or past about 30 turns (20 for Haiku) before acceptance, stop at a consistent point, write a handoff note (state, remaining steps, files touched, checks run) to a named path, and return it as partial.

Use only details that affect the assignment. Research returns relevant sources/files/symbols and a recommended boundary; review returns actionable findings with locations and expected behavior, without editing, and checks that new assertions would fail without the change; smoke returns observed coverage and gaps. Implementation returns its diff and check evidence. Save exact initial and revised briefs only when investigating handoffs or running a prompt-format pilot.

For mathematical or visual assertions, identify the actual board object or rendered element and the expected relationship; missing or empty data must fail the check. Preserve existing shared checks when adding a case-specific assertion.

Increment the brief revision when this template changes.

## Review and completion

Derive expected behavior from the spec, review the actual diff and surrounding code, and assess worker evidence. Use the specialist reviews and smoke workflow required by `AGENTS.md`; reuse sufficient checks unless integration or corrections invalidate them. Send repairs to the worker with the location, observed failure, and expected behavior. Repeated failure calls for reconsidering scope or approach. Final acceptance remains with the handler.

Assign extra implementation-worker screenshots where foreseeable layout risk warrants them or the worker needs them for its own verification; let the assigned release reviewer cover the remaining visual acceptance. Reserve deeper independent checking of mathematical premises for difficult mathematics, assumptions shared by dependent slices, or costly downstream rework. Required acceptance checks still apply. Focused repair is an ordinary completion path for local findings; choose preventive work according to the likely total effort through acceptance.

Run integrated acceptance at a stable checkpoint while relevant writers and dependency mutations are idle; record the revision and relevant dirty state. Reproduce failures observed during concurrent edits at that checkpoint before attributing them. Evidence predating relevant edits needs revalidation.

For build-tool, dependency, or artifact-format migrations, inventory affected auxiliary scripts as well as the app build (for example benchmarks, preview capture, and asset provenance). Record exercised commands or explicit coverage gaps. Close each actionable review finding with a verified fix or an explicit deferral and its impact; missing disposition is a gap.

Account for every acceptance criterion with observed evidence or an explicit gap. Distinguish implementation completion from acceptance completion: report partial acceptance while a required criterion is unmet or unverified, unless the owner explicitly revises or defers it. Preserve that deferral and its impact in the record.

Record accepted/blocked time and complete the [evaluation record](../.agents/skills/subagent-flow-evaluation/SKILL.md#do-log) from current-task evidence, then commit and push under the repository Git rules. Research, review, and smoke assignments count too; useful handler-only cases provide comparisons. Keep verification gaps explicit.

## Improve the workflow

Use [the evaluation skill](../.agents/skills/subagent-flow-evaluation/SKILL.md#suggest-subagents-flow-improvements) when assessing accumulated evidence. It connects both routing choices and task wording to outcomes. Load the log and research then, rather than on ordinary worker assignments.

The [v1–v6 assessment](agent-workflow/handoff-versions-2026-10-20.md) finds useful local instruction responses and clearer acceptance reporting, with no measured overall efficiency gain. The [v7 assessment](agent-workflow/handoff-v7-assessment-2026-10-24.md) found vacuous assertions recurring despite v7's wording; v8 adds observed-failure evidence and a reviewer non-vacuity check, plus persisted-data compatibility in Context. Their effect remains unmeasured. v9 adds the worker context budget as a [trial](specs/agent-workflow-evaluation.md#context-budget-trial--2026-10-24); v10 makes the handler send the handoff signal and gives Haiku a 100k budget. v11 sizes slices to about 20 turns, lowers the turn fallback, caps concurrency at three workers, and adds the Claude handler context budget after a run where the handler alone reached 458k ([evidence](agent-workflow/lesson-run-usage-2026-10-25.md)). v12 dispatches Claude workers through tool-restricted agents (startup about 9k instead of 37k), adds a launch hook that names each worker's watcher command, lowers the Haiku signal to 78k, and caps read size in the Budget field after a post-v11 Haiku research worker reached 119k in 22 turns without a watcher ([evidence](agent-workflow/haiku-context-2026-10-25.md)).

Compare total effort to accepted work, including implementation, verification, repairs, integration, and repeated setup where observable; report escaped defects separately. First-pass success or fewer repair rounds alone do not establish efficiency. Weigh added preventive checks against the repair work they could avoid, keeping unknown costs explicit.

Evaluate the worker budgets (100k Haiku, 150k others, turn fallback) with `tools/agent-usage/claude_turn_usage.py --since <trial start>`: keep it only if worker usage falls without more repairs, escaped defects, or longer completion. Compaction alone is not a failure or a reason to split work. Investigate context when it coincides with repeated reading, forgotten requirements, duplicate work, or excessive repairs; correlate the evaluation record's context note with observed symptoms. Treat smaller assignments or a fresh worker for a later role as hypotheses, accounting for repeated setup and lost familiarity. Judge comparisons by completion time, correctness, repairs, and scoped usage when available; fewer compactions alone do not establish improvement.

For a pilot, state the hypothesis and one changed factor before dispatch: model, effort, staffing, or brief wording. Compare similar roles, task classes, and preassigned sizes with stable acceptance and review. Use read-only repeats or isolated checkouts for duplicate trials; for repeatable comparisons on fixed tasks, use the [evaluation harness](../tools/agent-eval/README.md) (`just eval`). Report sample counts, missing data, and alternative explanations; no fixed small sample validates a default. Research pilots inform research routing. The owner may choose provisional defaults from external guidance; pilot results do not silently change policy. See the [evaluation spec](specs/agent-workflow-evaluation.md) for the maintained contract.
