# Codex handler context handoff

## Scope

Extend the existing [worker monitor](codex-worker-monitoring.md) to the calling Codex handler, following the [Claude handler workflow](../agent-workflow.md#handler-context-budget-claude). The user authorized implementation on 2026-10-25. This is developer tooling; application behavior is unchanged. Estimated size: M, one bounded monitor implementation plus handler-owned workflow/config integration.

## Acceptance

1. The existing dependency-free Node monitor supports `--self`, selecting exact session metadata ID from `CODEX_THREAD_ID`, with an explicit thread-ID override for fixtures. Reject conflicting worker/self selectors and ambiguous identities. Preserve existing worker defaults, events, and isolation.
2. Provide a bounded one-shot status command for self monitoring, reporting latest request input including cached input once, and distinguishing below-threshold, handoff, missing/unsupported telemetry, and errors. A historical completed turn's last input remains useful for a self snapshot; an active turn's crossing must survive a later lower sample. Never confuse cumulative usage or window capacity with request input. Background self monitoring must not stop merely because the handler waits on workers; document lifecycle/timeout behavior.
3. Follow the existing 150k soft / 190k handoff handler thresholds: stop starting work at soft threshold; at handoff threshold collect running worker notes, preserve consistent progress and verification state, and write a concise successor note. Workers retain the existing 135k signal / 150k budget. Use fresh-chat continuation with the handoff and current repository state, not inherited full history. Honor current Git rules; verified completed work goes to master, unfinished progress stays local with explicit state.
4. Add a concise always-loaded AGENTS.md pointer requiring handler checks at task start and bounded work boundaries, including handler-only tasks. Document that shell watchers cannot wake a hosted agent or create successor chats; the handler must consume status/events and use the available chat tool when supported. If continuation needs user input or creation fails, return the note and paste-ready prompt. No unattended shell model invocation or detached processes.
5. Configure project auto-compaction at 220000 total tokens, retaining child model settings. This is a fallback, not a hard 272k input cap or guaranteed subscription saving; large results and telemetry lag can overshoot. Keep source links to the official configuration/pricing documentation.
6. Focused Node tests cover self identity, conflicting selectors, snapshots below/at threshold, completion handling, batch crossings, unknown telemetry, and worker regressions. Demonstrate an assertion fails with the self selector/metric deliberately broken. Run a read-only live self status probe against this chat and record observed result without inflating its context. App build and browser smoke are inapplicable.

## Ownership and verification

One implementation worker owns monitor code and tests. Handler owns this spec, workflow/README, project configuration, AGENTS.md, integration review, live probe, evaluation record, and Git. Use Node's built-in test runner and focused lint; preserve concurrent unrelated changes. Record verification and any limitations here before completion.

## Verified result — 2026-10-25

- Implementation and read-only review used separate fresh workers, requested GPT-6 Luna High under handoff-v12. Worker monitoring retained its 135k trigger; both watcher terminal events reported completion below that trigger. The handler owned docs, configuration, integration, verification and Git. No application code changed.
- All 17 Node tests passed, including existing worker regressions and new self identity, guardian isolation, duplicate canonical IDs, legacy fallback, snapshot thresholds, previous-turn input, crossing persistence, missing telemetry and background completion. Focused `just lint` passed. Mutating the returned self identity caused an observed assertion failure (`deliberately-mutated` versus `session-1`); mutating observed input caused another (`0` versus `7`). Logs: `.command-logs/handler-monitor-mutation.txt`, `handler-monitor-metric-mutation.txt`, `handler-monitor-final-tests.log` (local, ignored).
- The first live self probe failed because actual guardian metadata uses its own `id` but its parent's `session_id`. The repaired discovery treats `id` as canonical, with legacy fallbacks only when absent; a realistic fixture protects parent/guardian isolation. The successful read-only probe returned `below_threshold` at 146557 input for exact thread `01a17539-0dac-78f3-ac58-92c05d419bc1`. A later real crossing returned `handoff_required` at 151531 input against the default 150000 threshold; recorded in `.command-logs/handler-monitor-live.json`. No context was inflated for testing and no 272k ceiling was tested.
- Independent review found no remaining monitor code defect. Its evidence-recording gap is addressed here. Relative link checks on the five affected Markdown files found no missing targets. The existing Developer tools workflow already runs this monitor test file on Windows and Linux; local verification was Windows only. App build and browser smoke were inapplicable.
- Saved-project discovery confirmed a local Bezeg project matching this checkout, and the current desktop exposes `create_thread`. Successor creation was not exercised end to end: the task finished at closeout, so no successor was needed. Other environments can lack that tool or matching checkout and must use the documented continuation prompt. The monitor cannot wake a handler or enforce a request cap.
- Configuration adds the documented 220000 total-token compaction setting, preserving child defaults. Reload in this already-running chat was not verified. A CLI strict-config probe could not validate it because `codex features` rejects `--strict-config`; no runtime-validation claim follows.
