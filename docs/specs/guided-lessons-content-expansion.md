# Guided lesson content expansion blueprint

**Status:** accepted implementation blueprint

**Source:** [Guided lesson rollout](guided-lessons-rollout.md), [current capability map](../capabilities.md), [ADR 0002](../adr/0002-guided-lessons-static-content-and-graph-capabilities.md), and the graph implementations under `src/graphs`.

## Goal

Expand Guided lessons to more active demonstrations in bounded, reviewable cohorts. A route receives a lesson only when its graph can expose the required operation through a typed graph-owned action, its default scene is deterministic, and its mathematics can be checked with a concrete observation or numerical invariant.

The expansion keeps Bezeg static and client-only. It does not add accounts, progress storage, a curriculum engine, new routes, or changes to Preset formats.

## Content contract for every route

Each lesson must provide:

- a stable `demonstrationId` and lesson ID;
- 4–6 ordered steps with a linear Explanation → Calculation when useful → Observation rhythm;
- Slovenian-first and English counterpart copy in the content module;
- at least two source records, including the implementation correspondence;
- one worked example or a precise invariant check;
- a prepared scene based on the route default, expressed only through supported scene actions;
- an explicit expected observation and edge-case note;
- no simulated clicks, hidden JSXGraph access, or direct Preset DTO dependence;
- inline mathematics in every prose field written as `\(...\)`, never bare TeX such as `B^n_i` or `Q_1`; formula and worked-example LaTeX fields stay undelimited. The lesson math-notation test enforces this for all lessons.

The runtime remains responsible for checkpoint capture/restore, animation cancellation, action adaptation, and failure rollback. Lesson content describes intent; graph classes own mutation and disposal.

## Cohort A implementation contract

The first expansion batch deliberately favors routes whose existing controls already express a coherent mathematical observation. Bernstein is deferred until its empty Preset and manually generated graph objects have a dedicated preparation/rebuild test.

### `rational`

Teach how weights change evaluation emphasis while the control polygon remains fixed. The lesson uses the existing weight labels, rational De Casteljau construction, and evaluation-point actions; it does not automate weight editing until a bounded positive-weight action has its own validation and lifecycle contract.

Checks:

- the default weights are `(1,2,1,1)`;
- the control polygon is unchanged while the evaluated point is controlled by the weighted Bernstein numerator and denominator;
- the rational result at `t=1/2` agrees with the existing rational evaluator;
- zero-denominator and non-positive-weight caveats remain explicit.

### `ph-quintic`

Teach the quintic PH curve as a curve generated by three hodograph vectors, then connect polynomial speed and offset distance to the visible offset curve. The lesson uses existing typed offset visibility and offset-distance actions; it does not simulate edits in the secondary hodograph board.

Checks:

- three hodograph generators produce a degree-five curve;
- the speed is the squared norm of the hodograph;
- changing the offset distance changes the offset display without changing the base curve;
- generated offset objects are disposed and restored on repeated lesson entry/exit.

### `bernstein`

Teach how the Bernstein basis functions form a partition of unity and how degree changes the number of basis functions. The lesson uses the default basis graph and graph-owned actions for degree and stacked-area visibility.

Required action seam:

- `bernstein-degree`: set degree/basis count in the valid range 0–5;
- `bernstein-stacked-area`: show or hide the stacked-area view;
- a prepared default scene that clears and regenerates graph-owned Bernstein objects before applying actions.

Checks:

- for degree 3, four basis functions are shown;
- each basis function is nonnegative on `[0,1]`;
- the basis sum is 1 on `[0,1]`;
- the stacked-area view is a visualization of the same sum, not a second mathematical model.

### `affine`

Teach that affine transformations act on the control points and commute with Bézier evaluation. The first lesson slice uses the route’s fixed default cubic curve and graph-owned translation and uniform-scale actions. Rotation and reflection remain a follow-up until their transform-center convention is made explicit.

Required action seam:

- `affine-transform` with a typed operation and bounded value;
- a prepared-scene hook that reapplies the route’s disabled generic Bézier controls after importing the default.

Checks:

- control-point coordinates transform as described;
- the degree and parameter interval remain unchanged;
- evaluating before then transforming agrees with transforming control points then evaluating, within the existing numeric tolerance;
- checkpoint restoration returns the original control points and graph state;
- rotation/reflection content is not released until its center semantics are documented.

## Cohort B implementation contract

Cohort B adds `bernstein` (contract above) and `rational-elevation`. Like Cohort A, a route may join the allowlist as a draft once route-level criteria 1–4 and 6 pass; criterion 5's owner language review and classroom review stay recorded as pending until completed.

### `bernstein` clarifications

- The graph state `n` counts basis functions; the degree shown in the counter and labels is `n − 1`. Lesson copy uses degree `n` in $B^n_i$, so the typed action is expressed as a **degree** in the integer range 0–5 and the graph maps it to `n = degree + 1`.
- The default lesson scene is degree 1 without the stacked-area view, matching the route's initial state. Preparing it disposes all graph-owned Bernstein objects before regeneration; repeated degree or view changes must not accumulate board objects or stale references.
- The stacked-area switch and degree counter must display the restored state after lesson Exit/Cancel.
- Non-integer, non-finite, or out-of-range degrees are rejected before mutating the graph.

### `rational-elevation`

Teach that rational degree elevation is ordinary degree elevation of the homogeneous control points $(w_iP_i, w_i)$, so both control points and weights change while the curve stays the same. Reuse the existing `degree-elevation` lesson action and rational weight-label visibility.

Required action seam:

- the existing `degree-elevation` action, owned by the rational elevation graph;
- a prepared-scene hook that reapplies the route's disabled generic Bézier controls after importing the default, as in `elevation`.

Checks:

- the default curve has control points $(-4,-3),(-3,3),(3,3),(4,-3)$ and weights $(1,2,1,1)$;
- one elevation gives weights $(1,\tfrac74,\tfrac32,1,1)$ and $Q_1=(-\tfrac{22}{7},\tfrac{15}{7})$, $Q_2=(-1,3)$, $Q_3=(\tfrac{13}{4},\tfrac32)$;
- $Q_1$ differs from the unweighted blend $(-3.25,1.5)$, which is the observation that distinguishes rational from polynomial elevation;
- elevated and original curves agree at representative parameters within the existing tolerance, including after two elevations;
- elevation uses the weights currently used for evaluation, and the weight labels show the elevated weights;
- checkpoint restoration returns the original degree, points, and weights.

## Cohort C implementation contract

Cohort C teaches that a curve and its parameterization are different things: the same point set can be traversed and sampled in different ways. Both routes draw generated sample points at parameters derived from equally spaced values $t_i=\tfrac{i}{N+1}$, $i=1,\dots,N$. Cohort A's allowlist rule applies.

`spline-parameterization` moved to cohort E after discovery: its α sets the C² spline's knot spacing (spans proportional to chord length raised to α), which moves the derived junction points and changes the curve's shape, not only its sampling. Teaching it needs the spline knot-spacing semantics reviewed with the other spline routes. Its α lives on the curve object rather than in graph state, so a future lesson must also make checkpoint restore reapply α.

### Shared action seam

- `parameterization-alpha`: α in $[0,1]$, finite;
- `parameterization-samples`: integer sample count in the route's UI range (1–40 on both routes);
- `parameterization-mode`: `weighted` or `uniform`, supported only by `uniform-parameterization`;
- each graph validates before mutating and rejects unsupported actions; the prepared default scene restores the route's initial α ($\tfrac12$), sample count (10), and, on the PH route, weighted mode;
- generated sample points are removed and regenerated by the owning graph without touching control points or hodograph inputs; checkpoint restore regenerates them and the α/count sliders and mode selector show the restored values.

### `weighted-parameterization`

Teach the rational reparameterization $\varphi_\alpha(t)=\dfrac{(1-\alpha)t}{\alpha(1-t)+(1-\alpha)t}$ on the route's fixed cubic Bézier curve. It satisfies $\varphi_\alpha(0)=0$, $\varphi_\alpha(1)=1$, is increasing for $0<\alpha<1$, and $\varphi_{1/2}(t)=t$.

Checks:

- $\alpha=\tfrac12$ leaves the samples at $t_i$;
- $\alpha=\tfrac14$, $N=3$ gives $\varphi(\tfrac14,\tfrac12,\tfrac34)=(\tfrac12,\tfrac34,\tfrac9{10})$, so samples crowd toward $P_3$;
- symmetry $\varphi_{1-\alpha}(t)=1-\varphi_\alpha(1-t)$; for $\alpha=\tfrac34$ the same samples sit at $(\tfrac1{10},\tfrac14,\tfrac12)$ and crowd toward $P_0$;
- the control points and the drawn curve are unchanged by α and by the sample count;
- $\alpha=0$ or $1$ collapses every interior sample to an endpoint; lessons use interior values and state the caveat.

### `uniform-parameterization`

Teach that a PH curve has polynomial speed $\sigma(t)=\lVert r'(t)\rVert$, so its arc length $s(t)=\int_0^t\sigma$ is a polynomial, and equal-arc-length samples solve $s(t_k)=\tfrac{k}{N+1}L$. Compare the weighted rule with uniform (arc-length) mode on the route's default PH cubic.

Checks:

- the implementation's $s(1)$ equals a numerical quadrature of $\sigma$ on $[0,1]$ for the default curve;
- in uniform mode consecutive samples satisfy $s(t_k)-s(t_{k-1})=\tfrac{L}{N+1}$ within $10^{-6}L$, and chord distances between consecutive samples are nearly equal;
- in weighted mode with $\alpha=\tfrac12$ the samples are at $t_i$, and their arc-length gaps are visibly unequal on the default curve;
- the inversion uses one predictor step and four Newton corrections, so lesson copy says "approximately equal" and does not claim exact equality;
- the lesson states the computed length $L$ of the default curve, taken from the implementation and checked by the content test.

## Cohort D implementation contract

Cohort D teaches that De Casteljau's construction splits a Bézier curve into exactly representing pieces and extends it beyond its interval. The graphs create new curves, so generated-curve ownership and restoration are the entry gate. Cohort A's allowlist rule applies.

### Discovery findings to resolve

- `subdivision` and `rational-subdivision` (`SubdivisionGraph1`, `RationalSubdivisionGraph2`) create an untracked orange curve in `initialize()` that captures the first curve object; after a lesson scene re-imports the default preset it can follow a disposed curve. The graph must own and rebind or recreate it.
- Subdivision sets `t` to 1 after splitting and hides the scheme; the scheme switch is keyed on graph state and must reflect restored state.
- `repeated-subdivision` (`SubdivisionGraph`) caps at five steps with `stepsDone`, which figure capture restores but lesson checkpoints do not; it also has a leftover `console.log`.
- Extrapolation routes replace the curve by its extension on $[0,t]$ with $t\in[1,1.5]$, and recreate the extrapolation point on deselect.

### Action seam

- `subdivision-parameter`: $t\in[0.01,0.99]$ on `subdivision` and `rational-subdivision`;
- `subdivide`: one split at the current parameter (subdivision routes), or one repeated-subdivision step at $\tfrac12$ (rejected after five steps);
- `extrapolation-parameter`: $t\in[1,1.5]$ on the extrapolation routes;
- `extrapolate`: one extrapolation at the current parameter;
- existing visibility actions (`decasteljau-scheme`, `control-polygon`, `weights`) where the graph already supports them;
- validation happens before mutation. The prepared default scene disposes every generated curve and auxiliary object, resets step counters and parameters, and re-creates route-owned auxiliaries. Checkpoint restore returns exactly the pre-lesson curves, points, weights, step count, and parameter.

### Checks

- `subdivision` at $t=\tfrac12$ on the default curve gives left control points $(-4,-3),(-3.5,0),(-1.75,1.5),(0,1.5)$ and right $(0,1.5),(1.75,1.5),(3.5,0),(4,-3)$; in general $L(u)=B(tu)$ and $R(u)=B(t+(1-t)u)$, checked at sample $u$ for several $t$;
- `repeated-subdivision`: after $k$ steps there are $2^k$ curves whose union traces the original, and the maximum distance between control polygon and curve decreases with $k$;
- `rational-subdivision`: the pieces are rational curves obtained by homogeneous De Casteljau; their evaluations match the original on the corresponding intervals;
- extrapolation: the extended curve $E$ satisfies $E(u)=B(tu)$, so it retraces the original on $u\in[0,\tfrac1t]$; the content states that growing $t$ moves control points quickly and that only $t\in[1,1.5]$ is offered;
- `rational-extrapolation`: the same identity holds with homogeneous coordinates for the default weights $(1,2,1,1)$. The extrapolated weights are $1,\ 1+t,\ 1+2t-2t^2,\ w(t)$; the third becomes zero at $t=\tfrac{1+\sqrt3}{2}\approx1.366$ and is $-\tfrac12$ at $t=1.5$. The original denominator $\sum_i b_{i,3}(s)w_i$ stays positive on $[0,1.5]$, so the extension has no pole and still equals $B(tu)$; a non-positive weight only means the new representation loses the convex-hull property. Lesson copy states this rather than claiming positive weights, and tests check the denominator on $[0,1.5]$;
- repeated lesson entry and exit leaves one curve and no stray auxiliary objects.

## Cohort E implementation contract

The owner supplied the subject-matter source: K. Štampar, *Orodje za grafični prikaz lastnosti Bézierjevih in PH krivulj*, master's thesis, University of Ljubljana (FMF/FRI), 2024. It documents Bezeg's own constructions, so lesson claims cite its sections and the implementation. The thesis does not treat the n-piece circle; that lesson uses the standard rational quadratic arc (Farin, *Curves and Surfaces for CAGD*). Cohort A's allowlist rule applies.

### Route claims and sources

- `decasteljau-alternative` (thesis §2.4, Izrek 2.13, Slika 6): $B_{[p_0,\dots,p_n]}(t)=(1-t)B_{[p_0,\dots,p_{n-1}]}(t)+tB_{[p_1,\dots,p_n]}(t)$. The graph draws the two degree-3 curves of its quartic, their points at $t$, and the segment between them. Check the identity at several $t$.
- `farin` (§3.2, Slika 17–18): $f_i=\frac{w_i}{w_i+w_{i+1}}p_i+\frac{w_{i+1}}{w_i+w_{i+1}}p_{i+1}$ divides $p_ip_{i+1}$ in the ratio $w_{i+1}:w_i$, and the weights follow recursively from $w_0=1$. Moving all Farin points to equal ratios gives geometric weights such as $1,3,9,27$, which standardize ($\tilde w_i=w_i/\sqrt[n]{w_n^{\,i}}$, Izrek 3.2) to $1,1,1,1$ with an unchanged curve. Check the ratios, the standard-form formula, and that standardization does not move curve points (only reparameterizes).
- `circle` (Farin; thesis §3 motivation): $n$ rational quadratic pieces on radius $r=3$ with half-angle $\alpha=\pi/n$; the middle control point is the tangent intersection at distance $r/\cos\alpha$ and has weight $\cos\alpha$. Every evaluated point lies at distance $3$ from the origin, and neighbouring pieces share endpoints and tangent directions. $n=2$ is degenerate ($\cos\tfrac\pi2=0$ sends the middle point to infinity), so the graph's minimum becomes 3 and lessons use $n\ge3$: each arc must be shorter than a half circle. Worked values: $n=3$ (120° arcs) gives middle weight $\tfrac12$ at distance 6; $n=4$ gives $\tfrac{\sqrt2}{2}$ at distance $3\sqrt2$. Sources: Farin, and Piegl & Tiller, *The NURBS Book* (Springer, 1997), chapter on conics and circles, which also shows that no polynomial curve represents a circle exactly.
- `spline-cn` (§4.2.1, Algoritem 3, Slika 24): one-sided construction, where each new piece takes its first $r+1$ control points from the extrapolation of the previous piece and the rest are free; degree $n$, continuity $r\le n-1$. Check $C^r$ at every junction (scaled derivatives equal up to order $r$) and that changing a free point of one piece changes later pieces (the thesis's user-unfriendliness note).
- `spline-c1` and `spline-c2` (§4.2.2, Algoritem 4–5, Slika 25–26): symmetric quadratic $C^1$ and cubic $C^2$ constructions; junction points divide segments in the ratio $\Delta u_l:\Delta u_{l-1}$, and with the route's uniform spacing they are midpoints (C¹) or the C² thirds/midpoint construction. Check $C^1$ resp. $C^2$ at every junction and locality of a control-point change.
- `spline-g1` (§4.1, (4.6), Slika 23): the next piece's second point is $p^{(2)}_1=p^{(2)}_0+b\,(p^{(1)}_n-p^{(1)}_{n-1})$, i.e. $b=1/\alpha_1$ in the thesis notation. Tangent directions match for every $b>0$; the derivative ratio equals $b$, so the spline is $C^1$ only for one value. The β slider currently shows 0.5 while the model starts at $b=1$; it must display the actual value.
- `spline-g1-symmetric` (§4.2.2, Algoritem 6, Slika 29): junctions $(1-\beta_l)p_l+\beta_lp_{l+1}$ with $\beta_l\in(0,1)$, starting at $\tfrac12$. Check tangent continuity for all β and how moving the junction changes the neighbouring pieces.
- `spline-parameterization` (§4.2.3, Slika 30): $\Delta u_i=\lVert\Delta p_i\rVert^\alpha$; $\alpha=0$ uniform, $\tfrac12$ centripetal, $1$ chordal. α changes both the spline's shape (knot spacing moves derived junction points) and the spacing of points sampled at equidistant global parameters. Its α lives on the curve, so the lesson checkpoint and default scene must reapply it.

### Action seam

- `spline-continuity` and `spline-degree` (integers within the route's current bounds) for `spline-cn`;
- `spline-beta` with an index and a value in the route's slider range (`spline-g1` $[0.01,3]$, `spline-g1-symmetric` $[0.01,0.99]$);
- `spline-label-points` and `spline-hide-fixed` for all spline routes (existing switches);
- `parameterization-alpha` and `parameterization-samples` (0–50) reused for `spline-parameterization`;
- `farin-points`, `standard-form`, and `rational-weights` (all weights finite and positive, one per control point) for `farin`;
- `circle-pieces` (integer, 3–12) for `circle`;
- the existing `parameter` action with `t` for `decasteljau-alternative`, which must also rebind its helper curves after every preset import (they are built only in `initialize()` today);
- every action validates before mutating, and the prepared default scene and checkpoint restore rebuild all derived points, helper curves, sliders, and switches.

### Data findings to report, not silently change

The `spline-cn` and `spline-c2` defaults each contain a three-number point (`[-1.5, -2, 5]`, `[1, -2, 5]`), probably meant as `-2.5`; the importer reads the first two numbers. Lessons describe the rendered default, and the owner decides whether to correct the presets (a visible default change).

## Route-level acceptance criteria

Before adding a route to `GUIDED_LESSON_AVAILABLE_IDS`:

1. Content tests verify step order, unique IDs, complete localization, supported scene actions, sources, and formula/worked-example references.
2. Graph tests verify each new action, default-scene preparation, operation bounds, and the relevant mathematical invariant.
3. Runtime tests verify catalog identity, prepared-scene adaptation, checkpoint restoration, and unsupported-action rollback.
4. The route is browser-smoke-tested through a direct `?learn=1` deep link, next/back/close flow, and a return to normal exploration.
5. The route is reviewed in Slovenian and English, at desktop/projection width and a narrow layout, with keyboard focus and touch-sized controls checked.
6. Documentation records the route, lesson status, action seam, and any remaining owner or classroom-review question.

## Explicit non-goals

- Do not expose a generic “learn” link for every graph.
- Do not teach an operation before its graph-owned action and disposal behavior are tested.
- Do not silently change routes, Preset identifiers, imported data, or stored browser presets.
- Do not call a draft classroom-ready until mathematical, language, accessibility, and device review is complete.
