# Handler-led coding-agent delegation

This note evaluates a workflow where the main agent owns scope, integration, and final review, while implementation workers take bounded slices. That shape is a reasonable inference when work divides cleanly, not a proven winning architecture. No cited source establishes the best model or effort for Bezeg. The owner adopted provisional task-fit defaults on 2026-10-15; [the workflow](agent-workflow.md) is authoritative. The [follow-up assessment](agent-workflow/external-evidence-2026-10-15.md) covers context costs and the reasons for simplifying evaluation.

## Evidence

OpenAI's [current Codex subagent guidance](https://learn.chatgpt.com/docs/agent-configuration/subagents), accessed 2026-10-15, describes Luna as a faster option for narrowly scoped work and GPT-6.1 Sol for demanding agents. It suggests High as a starting effort for Luna and reserves Max or xhigh for especially demanding reasoning; it also says increased effort costs time and tokens and may improve complex-task quality. This is task-fit guidance, not a benchmark of this repository or proof that replacing the earlier Luna Max default improves results. The [deployment checklist](https://developers.openai.com/api/docs/guides/deployment-checklist) recommends parallelizing independent tasks, avoiding parallel writers to shared mutable resources, and measuring quality, latency, and cost. These API recommendations inform the workflow rather than defining local desktop behavior.

OpenAI's [iterative repair example](https://developers.openai.com/cookbook/examples/codex/build_iterative_repair_loops_with_codex) separates review findings, repairs, and validation under a shared contract. Its [code-review guidance](https://developers.openai.com/blog/custom-code-review-rules-for-codex) keeps mechanical checks in CI and treats AI review as additional evidence alongside tests and approvals. The recommendation here is to combine handler review with executable checks rather than treating either agent's confidence as proof.

Anthropic's [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) describes orchestrator-workers as a fit for complex coding changes whose affected files and subtasks are hard to predict in advance. It says to use the simplest design that meets the need because agentic systems trade cost and latency for performance. Its parallelization guidance favors independent slices or distinct review perspectives; its evaluator-optimizer pattern fits work with clear evaluation criteria.

Anthropic's [multi-agent research system report](https://www.anthropic.com/engineering/multi-agent-research-system) found its orchestrator-worker system useful for breadth-first research, where agents can investigate separate directions in separate contexts. The report also says coding tasks often have fewer independent slices and more shared context. Its Opus 4 lead plus Sonnet 4 workers outperformed single Opus 4 by 90.2% on an internal research evaluation, while multi-agent systems used roughly 15× the tokens of chats. Those figures describe Anthropic's research system, not coding or this repository.

The official [Claude Code subagent documentation](https://code.claude.com/docs/en/sub-agents), accessed 2026-10-15, supports per-subagent model and effort settings, focused descriptions, scoped tools, isolated contexts, and concise result summaries; it recommends faster models such as Haiku for lower-cost tasks. Available effort levels and defaults depend on the model, and the resolved model can depend on provider and configuration. The [model configuration guide](https://code.claude.com/docs/en/model-config) says current Haiku 5.5 and Sonnet 5.5 support low through max effort and default to medium unless another setting applies. This establishes that role-based routing is available, not that a larger roster or mixed models improve Bezeg outcomes. These are implementation patterns, not comparative performance results.

Empirical work reinforces the need for task-fit. [CooperBench](https://arxiv.org/abs/2601.13295) evaluates two agents implementing separate features that may conflict; across its benchmark, collaborative success was on average 30% lower than the agents' individual results. The authors report vague or inaccurate messages, broken commitments, and mistaken beliefs about partners' plans. This is a direct-agent teamwork benchmark, so it warns about coordination but does not test a central handler assigning bounded slices and reviewing the patch.

The [Science of Scaling Agent Systems study](https://arxiv.org/abs/2512.08296), later published in [Nature Machine Intelligence](https://www.nature.com/articles/s42256-026-01268-y), compared single and multi-agent architectures under controlled tool and compute budgets across several benchmarks, including software engineering. Across its benchmark mix, it found that central coordination helped parallelizable tasks, while multi-agent variants hurt sequential reasoning and tool-heavy work. The authors' held-out architecture selection result was 87%; this does not mean an 87% gain in coding success. Neither this work nor the other sources compares Luna Max with other Luna effort settings.

## Initial Bezeg evidence (before the default revision)

At the initial review, the evaluation log contained six delegated product tasks, all in the demonstrations/homepage UI family and all using GPT-6 Luna Max: four used one worker and two used four or five workers. It also contained one handler-only workflow-documentation task, which is not a comparable code-task control. The entries show useful findings and repairs, but the delegated multiworker tasks cannot be fairly compared with the single-worker tasks because they differ in scope, staffing, acceptance coverage, and environment failures. Elapsed time and usage were unknown for every entry, escaped-defect status was unknown in three entries, and there was no alternate model or effort arm. This is an initial observational sample, not evidence that one staffing or model policy wins.

A possible effort pilot is repeated read-only research comparing Luna High with Max, or Haiku Medium with XHigh, holding model, task scope, sources, and handler review consistent. Record requested and observable resolved settings in research-role entries. Such a pilot informs research routing only; it does not establish implementation quality. If comparable tasks do not occur often enough, gather ordinary records rather than forcing a comparison.

## Recommendations for Bezeg

Keep one handler responsible for scope, task boundaries, integration, and final acceptance. Start with one implementation worker; add workers only for slices that are independent in both behavior and owned files. Give each assignment the source spec and acceptance criteria, explicit file or module ownership, dependencies, required checks, and existing changes to preserve. Require a report of changed files, behavior, checks, and unresolved risks. This follows Anthropic's warning that vague delegation causes duplicated work and gaps, and the repository's existing [workflow](agent-workflow.md).

The handler should derive expected behavior from the spec, inspect surrounding code, and review the actual diff and verification evidence. A worker's report is useful evidence, not acceptance. Keep reviewers read-only where possible, and send concrete findings back for repair. For files or interfaces shared by slices, assign one owner or serialize the work; worktrees can prevent direct edit collisions, but the handler still has to resolve integration and behavioral conflicts. Revisit repeated repair failures by narrowing or revising the assignment instead of adding more parallel workers.

Use the workflow's provisional defaults while capturing comparable outcomes and task-specific handoff evidence. General guidance motivates task-fit choices, but there is no repository-specific winning setting yet. The [evaluation skill](../tools/skills/subagent-flow-evaluation/SKILL.md) connects brief wording, clarifications, instruction changes, and observed outcomes to proposed improvements. It keeps model/effort comparisons separate from handoff hypotheses and supports owner-authorized provisional revisions without treating sparse observations as causal proof.
