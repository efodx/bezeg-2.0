# Three.js prototype lifecycle repair — 2026-10-26

The throwaway Three.js prototype now scopes async setup to a monotonically increasing generation. It checks ownership after the module import, fixture fetch, and fixture JSON read, so a remount or disposal during any wait prevents stale setup from allocating later resources, installing board listeners, or scheduling a render loop. Setup failures release partially created resources; stale failures are ignored. Readiness becomes true only after setup completes.

Toolbar and parameter-domain listeners now belong to the page lifetime, while renderer listeners, the resize observer, and the animation frame belong to one mount. Remount preserves the toolbar; final `dispose()` removes both ownership groups and is safe to repeat. A kind change made while the fixture is loading is applied when setup resumes, including the teapot view, which no longer evaluates a nonexistent single patch.

The smoke run also exposed a pointer failure: Three.js `Raycaster.setFromCamera()` returns no value. `rayFor()` now returns the raycaster after configuring it, allowing the caller to perform intersection queries.

`verify-three-lifecycle.mjs` executes the actual prototype source in a fake DOM/Three.js environment. Separate delayed schedules cover supersession during the module import, fixture fetch, and `response.json()`. It measures concrete effects before and after each stale continuation: renderer allocation for a stale import, whether a stale fetch reaches JSON parsing, and main-board listener/RAF counts for stale JSON completion. The old source reports ready before its fixture resolves, so readiness alone is not treated as evidence. Against pre-fix `be078cd`, all three schedules reproduce the corresponding failure; removing each individual generation guard from the current source also makes its matching schedule fail. The harness compares exact per-control listener counts across repeated remounts, checks final listener/RAF cleanup, and verifies `rayFor()` when `setFromCamera()` returns `void`. `verify-fidelity.mjs` and `git diff --check` pass. The harness does not establish browser rendering or pointer fidelity; the handler's independent served-copy smoke run remains the browser evidence.
