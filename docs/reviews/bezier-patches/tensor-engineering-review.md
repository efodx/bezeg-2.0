## Findings

- **P2 — Evaluation exposes a mutable cached value.** [`tensor-product-bezier-patch.ts`](../../../src/bezeg/impl/patch/tensor-product-bezier-patch.ts#L137) returns the `PointImpl` stored in `pointCache`. `Point` exposes coordinate setters, so a caller can mutate `patch.eval(u, v)` and poison the result of the next evaluation at that parameter; the same point can also be retained by a cached mesh. The mesh API avoids this by copying its cached result, but `eval` does not. The current identity assertion in the cache test confirms reuse without checking that callers cannot corrupt the cached value. Return a defensive point copy, or define and enforce a read-only evaluation result contract.
- **P2 — Evaluation and mesh caches grow without a bound.** `pointCache` retains every distinct exact `(u,v)` string key, and `meshCache` retains every interval pair. A continuous parameter drag while the control net is stationary creates a new point entry at each input value. Changing sampling density accumulates every previous mesh, with each mesh retaining O(uIntervals × vIntervals) points and faces. Bound/evict these caches or avoid caching transient continuous evaluations; constrain mesh sizes at the API boundary if callers can supply them directly.
- **P2 — Structural-replacement cache test does not prime a cache.** In the test at [`tensor-product-bezier-patch.test.ts`](../../../src/bezeg/impl/patch/tensor-product-bezier-patch.test.ts#L69), `setControlNet` runs before the patch is evaluated, so removing cache clearing/versioning would still pass. The point-edit test covers an evaluation cache hit/invalidation, but does not prime mesh or bounds caches before the edit. Prime each affected cache, replace the net or edit a tracked point, and assert new coordinates/mesh/bounds.
- **P2 — Triangular sampling semantics need one explicit rule.** The shared signature [`sampleMesh(uIntervals, vIntervals?)`](../../../src/bezeg/api/patch/bezier-patch.ts#L18) exposes two independent resolutions while task 06 requires a barycentric lattice. A triangular implementation can reuse the interface if it defines whether the second count must match the first (or how unequal counts map into the reference triangle); currently that contract is unspecified.

The version dependency path itself is complete for `PointImpl` stamps, structural `setControlNet`, and volatile/function-backed points: the implementation clears its caches on version changes and bypasses them for volatile inputs. Constructor validation rejects ragged/out-of-range nets and nonfinite coordinates; parameter and density checks reject nonfinite parameters and nonpositive/noninteger counts. Boundary and iso curves retain the documented captured-grid/live-point behavior.
