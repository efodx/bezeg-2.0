## 03D findings (profile + A/B, raw in job dir `C:\Users\1337Hacker\.claude\jobs\16d205a7\tmp\03d\`, may be gone)

- Orbit frames are style/layout/paint bound, not JS. In Chromium a path's `d` is a CSS property: each write cost ~4 µs style recalc (teapot 46 ms/move). `points` on polygon/polyline costs none → switched (`69b7ecb`).
- React re-render on a camera edit is ~1–2 ms (GraphHost, DemonstrationWorkspace, panels); not the bottleneck. JSXGraph's `pointerMoveListener` → `getMousePosition` forces `getComputedStyle` after our draw (harmless once nothing style-dirty is written).
- Sync vs rAF camera redraw, A/B on the same revision (board2d production, 2×16 moves): visible latency equal (tensor/triangular d8 ≈ 16.7 ms = 1 frame, d16 ≈ 33 ms = 2 frames, median); sync held the pointermove task 10–17 ms (next-rAF 2.3 → 9.5–16.6). Teapot visible 41.7 (sync) vs 48 ms (rAF). Decision: rAF (`973f521`); also coalesces non-frame-aligned input (wheel).
- `measure-app.mjs` cannot separate per-draw cost above one frame (it gates each move on rAF + Playwright round trip). Added a sustained-orbit probe `rate.mjs` (job dir; back-to-back `page.mouse.move` for 2 s, counts frames with a `points` mutation; ceiling ≈ 30 draws/s because Playwright waits for input handling). At `973f521`: teapot ≈ 17 draws/s, tensor-16 ≈ 31 (ceiling). Stride 4 or whole-segment runs did not raise the teapot.
- Teapot at `973f521` is bound by the DOM reorder: ~3250 `insertBefore` per draw = 9.2 ms JS + ~15 ms style recalc (moved nodes restyle); with moves disabled 16.7 → 30 draws/s. display:none nodes cost ~17%. Seam width irrelevant.
- Fix (handler design): **slot rebinding** — fixed-order `<polyline>` slots; each frame the k-th farthest drawable's geometry goes to slot k, attributes rewritten only when a slot's style changes; only point/marker ellipses move. Result (`7a47a55`, worker): teapot 28.2–28.8 draws/s (6 reps), tensor-16 49–54 — in a faster machine state than the 17/31 at `973f521`, so the gain is **not yet confirmed in one state**. New test: orbit `domMoves` ≤ points+markers, slots keep DOM order, DOM order = depth order (fails under two mutations). Risks: thin margin over the ≥ 28 target; triangles/planes are closed polylines (first point repeated); not smoke-tested; `measure-app.mjs` not run on it.
